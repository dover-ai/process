# Чек-лист безопасности

Проверяется от лица атакующего, а не от лица автора. Каждый пункт подтверждается выполненным действием: запрос и полученный ответ. Формулировка «проверено, всё в порядке» доказательством не является.

Заполненный пример в реальном проекте — [starter/docs/SECURITY.md](https://github.com/dover-ai/starter/blob/main/docs/SECURITY.md).

## Секреты и конфигурация

- [ ] Секретов нет в коде — настройки читаются из окружения
- [ ] Файл с локальными настройками исключён из репозитория
- [ ] В истории репозитория секретов нет; найденный однажды секрет считается скомпрометированным и заменяется
- [ ] Приложение не стартует в production с ключом-заглушкой
- [ ] Длина ключа подписи соответствует требованиям используемого алгоритма
- [ ] Правило зафиксировано тестом — его нельзя нарушить незаметно
- [ ] Секреты не передаются в аргументах командной строки: на общей машине они читаются соседним процессом

## Аутентификация

- [ ] Пароли хранятся только в виде хешей с индивидуальной солью, алгоритмом, предназначенным для паролей
- [ ] Пароль не попадает в логи ни при каких обстоятельствах
- [ ] Сравнение выполняется в постоянном времени
- [ ] Ответ на неверный пароль и на несуществующего пользователя **идентичен** — иначе перебираются зарегистрированные адреса
- [ ] То же касается времени ответа
- [ ] Отключённая учётная запись не проходит аутентификацию

## Доступ к данным

- [ ] Ограничение по владельцу стоит **в запросе к хранилищу**, а не применяется после выборки
- [ ] Проверено подстановкой чужого идентификатора: доступ к чужой записи не даётся
- [ ] Обращение к чужому объекту не подтверждает его существование
- [ ] Изоляция данных между пользователями закреплена тестами
- [ ] Права проверяются на сервере; ограничения интерфейса защитой не считаются

## Ввод и вывод

- [ ] Все входные данные проверяются по схеме
- [ ] Ограничены длины строк и размеры загружаемых файлов
- [ ] Ограничены параметры постраничного вывода
- [ ] Запросы к хранилищу параметризованы
- [ ] Наружу отдаются только перечисленные поля
- [ ] Сообщения об ошибках не раскрывают устройство системы

## Транспорт и доступность

- [ ] Соединение шифруется; где терминируется — зафиксировано
- [ ] Служебная документация закрыта в production
- [ ] Ограничение частоты запросов настроено либо внесено в реестр ограничений
- [ ] Правила обмена с другими источниками заданы явно, а не разрешены всем

## Развёртывание

- [ ] Процесс работает не от привилегированного пользователя
- [ ] В образ не попадают файлы настроек, тесты и служебные каталоги
- [ ] Секреты передаются через окружение, а не запекаются в слои образа
- [ ] Зависимости проверены на известные уязвимости
- [ ] Есть способ узнать, что процесс жив

## Данные при разработке

- [ ] Исполнитель работал с очищенной копией: белый список каталогов, поиск персональных данных и секретов выполнен, список найденного приложен к решению о данных
- [ ] В репозитории нет фикстур, дампов и выгрузок с реальными персональными данными; тестовые данные синтетические
- [ ] Логи для разбора инцидентов — только обезличенный фрагмент от заказчика или разбор на его стороне
- [ ] Все внешние сервисы, через которые прошли код и данные, перечислены в решении о данных

## Процесс

- [ ] Линтер с правилами безопасности выполняется на каждое изменение
- [ ] Проверки блокируют слияние, а не сообщают о проблеме постфактум
- [ ] Код вносит служебная учётная запись исполнителя, одобряет инженер своей; ветка защищена правилом «одно одобрение не от автора» — проверено попыткой слить запрос без одобрения
- [ ] Проверено, что защита действительно срабатывает: сломай правило намеренно — сборка обязана упасть

Последний пункт закрывает самый неприятный класс проблем: проверка, которая молча пропускает всё. Она выглядит работающей, отчёт зелёный, а механизма нет. Такое обнаруживается только живым прогоном с заведомо плохими данными.

---

Незакрытые пункты — не признак плохой работы, если они осознаны и внесены в реестр ограничений с приоритетом. Признак плохой работы — незакрытые пункты, о которых заказчик не знает.
