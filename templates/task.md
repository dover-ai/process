# ID. Название задачи

Шаблон файла задачи — шины, через которую работа передаётся между ролями (см. [PROCESS.md](../PROCESS.md)). Следующей роли передаётся список артефактов, а не история рассуждений: в журнал пишутся ссылки, а не выводы.

**Исключение — верификатор.** Файл задачи он не читает: здесь видно, кто выдвинул утверждения и зачем, а [протокол независимой проверки](../VERIFICATION.md) запрещает это передавать. Верификатор получает только задание на проверку ([шаблон](verification-request.md)). Строку в журнал за него дописывает тот, кто ведёт задачу.

---

## Контекст

Заказчик (как к нему обращаться), фаза процесса, повод, читатель итогового результата.

## Параметры проекта

Подтверждает владелец при постановке; роли берут цифры отсюда, а не из своих допущений.

| Параметр | Значение | Источник |
|---|---|---|
| Ёмкость на проект, ч в неделю | | решение владельца; по умолчанию 8 ([PROCESS.md](../PROCESS.md), «Подбор объёма под срок») |
| Ставка для расчёта | | коммерческие правила студии или решение владельца |
| Политика прототипа | уровень, оплата | [PROCESS.md](../PROCESS.md), «Прототип к предложению» |
| Отступления от коммерческих правил | | решение владельца |

## Цель

Что должно появиться на выходе — артефакты, которые можно открыть и проверить.

## Ограничения

Что запрещено (доступы, данные, правки), что считается фактом, язык и тон.

По умолчанию: **выход в сеть запрещён всем ролям**, кроме верификатора, которому доступ задаётся в задании на проверку; исключения называются явно. Для каждого артефакта — лимит объёма, у длинных документов — сводка в начале.

Утверждения того, кто ведёт задачу, если они попадают к заказчику, проходят верификацию наравне с утверждениями ролей: сведения «по памяти» — тоже гипотезы.

## Входные материалы

| Файл | Что внутри |
|---|---|
| | |

Копии источников — текст, извлечённый из страниц и документов, — теряют символы: например, знак «>» перед числом. Числа и знаки из копий перед использованием сверяются с оригиналом.

## Маршрут и границы записи

| Шаг | Роль | Описание роли | Пишет в | Не трогает |
|---|---|---|---|---|
| 1 | | `roles/….md` | | |

**Документ для заказчика проходит две проверки с его позиции:** экспертное чтение сводки решения — до писателя, чтобы предметные ошибки находились до того, как написан текст; проверка готового текста не автором — после. Рекомендации попадают в документ только из решения архитектора.

**Вводные заказчика замораживаются до запуска писателя.** Вводная, пришедшая позже, записывается в раздел «Новые вводные» и обрабатывается перезапуском шага, а не сообщением в работающий процесс.

**Длинные шаги** — дольше получаса — не запускаются перед закрытием сессии; роль сохраняет промежуточный итог в свой артефакт, чтобы при обрыве шаг продолжился, а не начался заново.

## Контракты вывода

Структура результата каждой роли — ссылкой на шаблон: [ADR](adr.md), [перечень рисков](risk-register.md), [задание на проверку](verification-request.md), клиентский документ на [бланке](client-document.md).

## Журнал

**Журнал ведёт только тот, кто ведёт задачу.** Роли не дописывают сюда строки сами — они возвращают список созданных артефактов, и строку вносит ведущий. Иначе роли, работающие параллельно, затирают записи друг друга.

**Время ИИ-исполнителя — по системному учёту запуска**, а не со слов роли: роли путают часы и длительность. Часы инженера записываются в момент решения или приёмки; если владелец называет время общим итогом — так и пишется, с пометкой.
